# SupportFlow 面试问答(12 题)

每题含:问题、60–120 字口头回答、关键代码位置、可补充的技术细节、必须承认的边界。所有回答基于本仓库实际实现,不假设不存在的功能。

---

### 1. 为什么选择 LangGraph,而不是简单的 if/else?

**口头回答**:退款工单不是一条直线流程:低风险可以自动执行,高风险要停下来等人工审批、批准后从中断点带着上下文继续,失败还要区分可重试与不可重试。用 if/else 写,这些状态会被摊平在代码各处,暂停-恢复的语义要靠自己保存和重建。LangGraph 给了我显式的图结构、节点间条件路由、每个节点的状态传递,以及 `recursion_limit` 这种兜底保护。但要注意,图只负责编排,不做决策——钱的规则都在服务层。

**代码位置**:[app/agent/graph.py](app/agent/graph.py)(10 个节点、条件路由)、[app/agent/runner.py](app/agent/runner.py)(`recursion_limit`)。

**补充细节**:审批暂停后「重跑同一个 ticket」即恢复:图在审批节点复用存储的计划并重验,不重新咨询 LLM;LangGraph 自身的递归保护位于我们自己的迭代上限之上,双保险。

**边界**:图本身不保证业务正确性——绕过图直接调服务,安全校验同样成立,这是有测试保证的。

### 2. Agent(LLM)如何与确定性的退款服务分工?

**口头回答**:LLM 只做三件事:把工单归类、把上下文整理成计划提议、把结果写成回复。任何涉及钱的决定它都碰不到:订单归属、金额、政策、审批、幂等全部在 RefundService 里用可信记录重算——工单绑哪个订单以工单记录为准,LLM 传错 issue_type 直接被拒。工具列表是固定的,模型不能选工具、不能直接调网关。相当于 LLM 是「会读写的实习生」,服务层是「财务系统」。

**代码位置**:[app/services/refunds.py](app/services/refunds.py)(校验链)、[app/tools/registry.py](app/tools/registry.py)(固定工具集)。

**补充细节**:分类、计划、回复各有 2 次有界重试,失败回退确定性离线实现,所以无 Key 也能完整演示。

**边界**:LLM 产出质量(分类准确率等)没有做过评测,只验证了「LLM 输出错误时系统仍安全」。

### 3. 如何避免重复退款?

**口头回答**:三层。第一,全意图幂等键——把工单、订单、金额、计划版本绑成一个键,数据库唯一约束兜底,重放请求解析到原记录,不会建第二行。第二,同订单同时间至多一笔未决退款,靠部分唯一索引实现。第三,结算本身幂等:行锁下重查状态,已终态的直接返回,双进程并发 finalize 的集成测试里恰好结算一次。异常路径也幂等:网关异常记 UNKNOWN,同键重试走查询原操作而不是新执行。

**代码位置**:[app/persistence/pg_refund_store.py](app/persistence/pg_refund_store.py)(`create`/`finalize`)、[app/persistence/models.py](app/persistence/models.py)(`uq_refunds_idempotency_key`、`uq_refunds_order_unresolved`)。

**补充细节**:同键不同意图会被明确拒绝为 `conflict`(绝不静默接受);同键同意图无论原记录在什么状态都有确定性的解析分支。

**边界**:这保证的是「系统侧不重复」;若真实网关自身无幂等窗口,执行侧崩溃窗口的二次执行风险属于网关契约,没有假装解决。

### 4. 为什么需要预留额度(reservation)?

**口头回答**:退款不是一步完成:从创建到网关确认有时间窗,这期间余额的归属必须被锁住。如果只记「已退款」不记「在途」,一个并发请求就能把同一笔可退余额再花一次。所以创建时在同一事务里条件更新预留:`refunded + reserved + amount <= total` 不满足就不放行;网关确认后预留转入已退款,失败释放,结果未知保留。这是 fail-closed:不确定时宁可多占着,也不冒险放走。

**代码位置**:[app/persistence/pg_refund_store.py](app/persistence/pg_refund_store.py)(`_create_new` 条件 UPDATE、`_move_balances`)。

**补充细节**:为什么用条件 UPDATE 而不是先读后写?先读后写在两个事务交错时会基于过期读数互相覆盖;条件 UPDATE 在行锁上原子判定,`rowcount==0` 就是失败。库级 CHECK `refunded + reserved <= total` 是最后防线。

**边界**:预留长期滞留(UNKNOWN 无人恢复)会占着额度——这是 fail-closed 的代价,需要恢复机制兜底,本项目恢复需外部触发。

### 5. 为什么数据库事务不能包住外部网关调用?

**口头回答**:因为网关调用可能几秒甚至超时,事务期间持有的行锁会让其他请求全堵住;更根本的是,网关不是事务参与者——本地提交了网关失败、或者网关成功本地回滚,两者无法一起回滚。所以我把它们拆成三段:先在一个短事务里完成校验、预留、落 PENDING 行并提交;然后调用网关(无锁);最后用新事务按网关结果 finalize。留下的窗口——执行了但没 finalize——由恢复服务用「查询原操作」来收敛。诚实地说:不原子就是不原子,靠查询和幂等收敛,而不是假装原子。

**代码位置**:[app/services/refunds.py](app/services/refunds.py)(`create` → `_execute` → `_apply_gateway_outcome` 三段)、[app/services/recovery.py](app/services/recovery.py)。

**补充细节**:refund_id 在网关调用之前落库,所以恢复查询键永远指向原始操作,包括进程恰好死在中间的那一笔。

**边界**:真正彻底消除窗口需要网关侧幂等键支持;当前项目在模拟网关上验证了收敛逻辑,真实网关未验证。

### 6. UNKNOWN 与 FAILED 有什么区别?

**口头回答**:FAILED 是「有确凿证据这笔退款没有执行,也没有相同操作在处理中」——比如网关明确返回暂时失败。UNKNOWN 是「没有证据,不确定」:超时、连接中断、查询失败、处理中、索引延迟都是 UNKNOWN。区别在于对钱的处置:FAILED 可以安全释放预留;UNKNOWN 必须保留预留并等待查询澄清。因为异常说明不了结果——连接可能在钱已经划走之后才断。把 UNKNOWN 当 FAILED 释放预留,就可能钱退了、额度又被别人用掉。

**代码位置**:[app/services/payments.py](app/services/payments.py)(`GatewayQueryResult` 三类契约)、[app/services/refunds.py](app/services/refunds.py)(`_execute` 异常一律 UNKNOWN)。

**补充细节**:UNKNOWN 的行在恢复服务中「始终合格」——因为只有反复查询才能等到确凿答案;而终态行永不移动。

**边界**:三类结果的准确性依赖网关契约本身——替身网关的分类是写死的,真实网关怎么把各种错误映射到这三类,未验证。

### 7. 为什么恢复服务查询原操作而不重试执行?

**口头回答**:因为重试执行是在猜:「上次超时,这次再打一笔」——如果上次其实成功了,这就是第二笔钱。查询则是问网关:「这笔(refund_id)到底怎么样了?」拿到了确凿证据才动本地状态:SUCCEEDED 结算,FAILED 释放,否则继续等。所以我的恢复服务在结构上就没有执行路径——它只依赖 `query_status` 接口,构造时校验这个能力,模块里根本不存在调用 execute 的代码。租约过期也只意味着允许再查一次,绝不意味着允许再执行。

**代码位置**:[app/services/recovery.py](app/services/recovery.py)(构造校验、无 execute 路径)、测试断言 `gateway.execute_calls == 0`。

**补充细节**:refund_id 是稳定查询键(执行前落库),所以查询永远指向原始操作,包括崩溃窗口里的那笔。

**边界**:前提是网关侧查询可靠;真实网关的查询接口、延迟窗口(如索引延迟多久可见)未验证。

### 8. 数据库租约与行锁分别解决什么问题?

**口头回答**:行锁解决「同一时刻只能有一个事务改这行」——结算前 `FOR UPDATE` 加状态复查,保证不重复结算。但恢复的流程是「查网关 → 再写库」,中间隔着网络,不可能拿着行锁去查网关,那会把锁占几秒钟。租约解决的是这段时间的归属:一条原子条件 UPDATE 把行标记为「worker X 拥有到 T 时刻」,只有一个 worker 能成功;查完网关再写库时,校验 owner token 还在不在——不在就说明租约过期、别的 worker 接管了,我的证据已经作废。行锁管事务内,租约管跨事务的时间窗。

**代码位置**:[app/persistence/pg_refund_store.py](app/persistence/pg_refund_store.py)(`claim_recovery` 条件 UPDATE、`settle_recovered` 锁 + owner 校验)。

**补充细节**:租约过期只是「允许重新查询」的信号,它改变不了「恢复不执行」这个前提;claim 把 `recovery_attempts + 1` 作为重试节奏的可见记录。

**边界**:租约过期时间的选择是运维参数;过长拖慢接管,过短造成无谓重复查询(只读,无害)。

### 9. 如何防止旧 worker 的迟到结果覆盖新状态?

**口头回答**:核心是「每次写入都验证你的证据是否仍然有效」。worker A 查到 SUCCEEDED 但网络卡了,租约过期;B 接管后发现证据变了、把行保持在 UNKNOWN。A 回来想结算时,结算事务先 `FOR UPDATE` 锁行,再看两件事:行还是不是未决状态、租约 owner 还是不是 A——两个条件任一不满足就返回 `lost_ownership`,一行都不写。于是 A 的过期结果被丢弃,B 写下的状态原样保留。终态同理:已经被结算的行,任何 worker 都写不进去。

**代码位置**:[app/persistence/pg_refund_store.py](app/persistence/pg_refund_store.py)(`settle_recovered`/`mark_recovery_kept_unknown` 的 owner token 校验)。

**补充细节**:集成测试 `test_stale_worker_cannot_overwrite_newer_state` 完整模拟了这个场景,断言 A 的迟到结算返回 `lost_ownership` 且账务为零变化。

**边界**:owner token 是随机 UUID,校验的是「同一个 worker」;租约过期时间本身可能被配得太长,导致接管延迟——这是参数问题,不是正确性问题。

### 10. 如何确保余额、状态和审计事件保持一致?

**口头回答**:把三样东西放进同一个数据库事务。每个 store 操作——创建、结算、释放、恢复——都在一个事务里同时更新订单余额、退款行状态和一条审计事件,提交则全有,回滚则全无。集成测试里专门做了故障注入:让审计写入抛异常,断言整个结算回滚——状态没变、预留还在、审计里没有孤儿记录。这意味着审计永远不会显示数据库里不存在的状态:你看到一笔「已结算」,账上就一定动了那一笔。

**代码位置**:[app/persistence/pg_refund_store.py](app/persistence/pg_refund_store.py)(各路径同一 `session_scope` 内写审计)、[app/persistence/models.py](app/persistence/models.py)(`audit_events` 外键)。

**补充细节**:审计事件带 actor/action/关联 ID/明细,且只带退款标识,不写密钥与客户敏感字段;外键保证审计引用的退款、运行记录真实存在。

**边界**:一致性覆盖「数据库内」的原子性;网关侧动作不在事务里(见第 5 题),这是刻意设计而非缺陷。

### 11. 当前测试能证明什么,不能证明什么?

**口头回答**:能证明:262 个单元/图测试覆盖决策逻辑、工具边界、状态机与静态守卫;51 个集成测试在真实 PostgreSQL 16 上验证了行锁、条件更新、唯一索引、审计原子性和恢复闭环,包括 spawn 双进程的竞态、约束直测和故障注入回滚——这些是「在这些场景下行为符合设计」的经验证据。不能证明:它对所有并发交错都正确(并发正确性没有做形式化验证);真实网关下的行为(网关是替身);任何生产负载下的性能。测试通过不等于数学证明,这个边界我不会模糊。

**代码位置**:[tests/integration/](tests/integration/)(51 个 PG 集成测试)、[tests/](tests/)(262 个单测)。

**补充细节**:集成测试要求专用测试库且库名以 `_test` 结尾,防误连;未配置测试库时直接跳过,不假装跑过。

**边界**:LLM 输出质量、真实网关契约、部署环境(全新机器)均未验证。

### 12. 如果接入真实支付网关,最先需要验证哪些契约?

**口头回答**:我会按风险顺序验证四件事。第一,执行幂等窗口:网关是否支持客户端幂等键、窗口多长——这决定「执行侧崩溃窗口」的真实暴露面。第二,状态查询契约:查询按什么键、返回什么、三类结果(SUCCEEDED/FAILED/UNKNOWN)如何映射、索引延迟多久可见——这决定恢复服务能不能照搬。第三,资金语义:预留/撤销/最终结算在网关侧分别是什么原语,我们的 FAILED 释放对应哪个。第四,鉴权与限流:查询和执行的凭证、速率,以及它们对恢复扫描频率的约束。任何一条对不上,都要先改适配层和恢复参数,而不是先上线。

**代码位置**:网关隔离在 [app/services/payments.py](app/services/payments.py)(`PaymentGateway` / `RefundStatusQuery` 协议)——真实网关应实现同一协议;恢复侧 [app/services/recovery.py](app/services/recovery.py) 只依赖查询协议。

**补充细节**:本项目刻意把网关放在协议后面,就是为了换真实实现时不需要动服务层和恢复层。

**边界**:以上全部是「需要验证的清单」,不是已经验证的事实——当前没有任何真实网关凭证或测试环境。
